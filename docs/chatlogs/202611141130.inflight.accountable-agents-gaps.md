## Source

Thomas Gessler's two public concept papers. Cite these, and only these, in this repo:

- *Declarative AI Architecture: Knowledge Artifacts as System Logic for Generative Systems*, DOI 10.5281/zenodo.20687710
- *Accountable Agents: Declarative Control Architecture for Operational AI Systems*, DOI 10.5281/zenodo.21850919

The ideas used here, in our words:
- A control counts as external only if the governed agent cannot change, disable or get around it.
  Sitting outside the model is not enough.
- A negative test passes only if the intended control was active and caused the failure.
- A failure to run is a different outcome from "no decision". The papers name six final states:
  act, refuse, block, defer, escalate, non-decision.
- Declared controls should be checked against what actually runs, before deployment.
- To measure drift, record the version of the method that ran.

Rapier already meets much of this. The method is declared in a manifest outside the models. The
models only answer API calls and have no tools. Review is cross-vendor and says so when it isn't. The
run record names each stage, model and vendor. And a verifier error on one artifact gives `flagged`,
never `clean` (`src/rapier/verify/_vendor/spar_verify_gate.py`, `decide()`). The items below are at
the edges.

## Items, most useful first

### 1. SCOPE-CANDIDATE: the calling agent can switch a check off (about half a day)
Over MCP the calling agent picks `verify` (`src/rapier/mcp/server.py`, `spar` / `sparring`).
`verify="off"` drops the citation gate and the Proposer's traceability gate (`src/rapier/presets.py:73`
and `:117`). The definitiveness gate always runs. So the agent whose output is being checked chooses
which checks run.
- `verify_mode` is recorded in `ceremony.json`. Not yet checked: whether the report tells the reader.
- Proposal: a minimum level the operator sets (env or config) that a tool argument can't lower, and a
  report line naming any check that was turned off, and by whom (caller argument or operator config).

### 2. BUG-CANDIDATE: "didn't run" reads like "found nothing" (small)
When the definitiveness verdict is missing, `_verdict_sentence` in
`src/rapier/stages/resolver/compose.py` (around line 47) says "there were no hard specifics to check,
or the checker was unavailable". That merges a check that ran and found nothing with a check that
never ran. A stage that raises is also caught and logged, and the pipeline goes on
(`src/rapier/pipeline.py:150`, fail-soft), so a crashed gate lands in the same message.
- Proposal: separate outcomes (`not-run: <reason>` and `nothing-to-check`) in the verdict, the Trust
  Rider and `ceremony.json`.

### 3. SCOPE-CANDIDATE: compare what the manifest declared with what ran (about half a day)
- At run time: the Trust Rider lists each declared stage and whether it produced a result, failed soft,
  or was skipped. `ledger.jsonl` holds the trace tails today, but nothing compares them with the
  manifest.
- Before a run (`rapier doctor` or manifest load): warn when a manifest declares no correctness gate,
  or when a gate's result never reaches the verdict.

### 4. DESIGN-CALL: name the final outcomes
PASS / FAIL / REVIEW / unchecked map roughly onto block and defer. SPARRING has no formal
non-decision. A Proposer phase that exits at its cap still in disagreement (`stages/proposer/phase_stages.py`,
"disagreement-at-cap") is a non-decision: label it, and say what the reader should do next. Keep it
apart from "a check failed to run" (item 2).

### 5. SCOPE-CANDIDATE: record the method version (small)
`ceremony.json` has `sparring_version`, and the transcript has the models. There's no hash of the
manifest (resolved pipeline plus config) that actually ran. Add one, so we can tell whether the same
inputs under the same method version still give the same result.

### 6. DESIGN-CALL, optional: strict single-vendor mode
With one vendor available, the reviewer runs on the author's vendor and the report says it is "not an
independent check". A strict mode would stop and report that no independent check is possible,
instead of going ahead.

## Out of scope
Rapier only gives advice and never acts on anything, so the papers' commit boundary and "act is not
commit" don't apply. Their rule that conflicting validators must not produce a commit is met by
reporting: objections appear in a "contested" section rather than being merged away.
